# Tasks: generation-service

Каждая задача проверяется по принципу TDD: сначала тест, потом реализация. Порядок — по фазам; внутри фазы задачи зависимы сверху вниз.

## 1. Каркас проекта и окружение

- [ ] Тест: `pytest` запускается на пустом проекте (smoke-тест `test_smoke.py`). Реализация: `pyproject.toml` (uv, Python 3.13, Black, pytest, pytest-asyncio), структура `src/`.
- [ ] Тест: конфиг читается из env с дефолтами (`test_config.py`). Реализация: `src/config.py` (DATABASE_URL, PROVIDER_TIMEOUT, HMAC-секрет, FAKE_PROVIDER_ADMIN_ENABLED).
- [ ] Тест: приложение создаётся через фабрику (`create_app`) и поднимается на ASGITransport. Реализация: `src/main.py` с lifespan.
- [ ] Реализация: `Dockerfile` (multi-stage, gunicorn + UvicornWorker, 4 воркера) и `docker-compose.yml` (PostgreSQL + сервис + провайдеры). Проверка: `docker compose up` поднимает 3 контейнера.
- [ ] Реализация: Alembic-инициализация (`alembic init`, `env.py` с async engine). Проверка: `alembic upgrade head` на пустой базе.
- [ ] Реализация: `src/telemetry/` (OpenTelemetry-модуль, `OTEL_ENABLED=false` по умолчанию, no-op при выключенном).

## 2. Модели и миграции

- [ ] Тест: модели импортируются и маппятся на таблицы (`test_models.py`). Реализация: `src/database/models.py` — `User`, `LedgerEntry`, `Payment`, `Model`, `Leg`, `Task`, `Attempt`, `WebhookEvent`.
- [ ] Тест: миграция создаёт все таблицы и ограничения (проверка схемы после `upgrade head`). Реализация: первая ревизия Alembic.
- [ ] Тест: `CHECK (balance >= 0)` отклоняет отрицательный баланс. Реализация: ограничение в миграции.
- [ ] Тест: уникальные ключи идемпотентности существуют (`(task_id,kind)` для debit/refund, `payment_id` для topup, `(provider,event_id)` для webhook_events). Реализация: partial unique индексы/констрейнты в миграции.
- [ ] Тест: data-миграция наполняет каталог (`image-fast`, `video-long` и их ноги). Реализация: data-миграция Alembic.

## 3. Домен денег (ровно один раз)

- [ ] Тест: `debit` создаёт строку журнала и уменьшает баланс атомарно. Реализация: `src/services/uow.py` — Unit of Work, `LedgerService.debit`.
- [ ] Тест: повторный `debit` по той же задаче откатывается по уникальному ключу. Реализация: обработка IntegrityError → no-op/rollback.
- [ ] Тест: `refund` создаётся ровно один раз при 10 конкурентных вызовах. Реализация: `LedgerService.refund` с уникальным `(task_id,'refund')`.
- [ ] Тест: `topup` создаётся ровно один раз при 20 конкурентных одинаковых оплатах. Реализация: `LedgerService.topup` + `Payment` с уникальным `payment_id`.
- [ ] Тест: баланс всегда равен сумме журнала после серии операций. Реализация: запрос `sum(ledger)` и проверка инварианта.
- [ ] Тест: операция, ведущая баланс в минус, отклоняется. Реализация: опора на `CHECK (balance >= 0)` внутри транзакции.

## 4. Фейковые провайдеры

- [ ] Тест: `POST /tasks` возвращает `202` с `external_id`. Реализация: роут провайдера.
- [ ] Тест: провайдер шлёт вебхук `completed`/`failed` с HMAC-подписью. Реализация: фоновая отложенная отправка вебхука (2–20 с).
- [ ] Тест: настраиваемые доля отказов и тип ошибки. Реализация: чтение настроек из env/`PUT /_settings`.
- [ ] Тест: синхронный отказ (503/таймаут на `POST /tasks`). Реализация: режим sync-failure.
- [ ] Тест: повторный `POST /tasks` с тем же `attempt_id` возвращает тот же `external_id`. Реализация: идемпотентность провайдера по `attempt_id`.
- [ ] Тест: вебхук приходит дважды (в т.ч. одновременно). Реализация: режим дублирования вебхуков.
- [ ] Тест: `PUT /_settings` доступен только при `FAKE_PROVIDER_ADMIN_ENABLED=true`. Реализация: guard-флаг.

## 5. Каталог и выбор ноги

- [ ] Тест: выбор первой подходящей ноги по приоритету. Реализация: `src/services/legs.py` — `select_first_fitting_leg`.
- [ ] Тест: нога подходит по `max_ref_images >= len(ref_images)`. Реализация: предикат подходящести.
- [ ] Тест: ни одна нога не подходит → 400 до списания. Реализация: валидация в `POST /generate`.
- [ ] Тест: `skip_on_moderation`-нога пропускается после moderation-отказа. Реализация: фильтр следующей ноги по контексту отказа.

## 6. Генерация (POST /generate)

- [ ] Тест: успешный заказ списывает цену, создаёт задачу и возвращает `task_id`. Реализация: `POST /generate` handler + use-case.
- [ ] Тест: 402 при недостатке токенов. Реализация: проверка баланса.
- [ ] Тест: 429 при 3 активных задачах (проверяется раньше 402). Реализация: подсчёт активных (`pending`/`running`) с блокировкой пользователя.
- [ ] Тест: цена снапшотится в `tasks.price_tokens`. Реализация: сохранение цены при создании задачи.
- [ ] Тест: создаётся попытка и отправляется первой подходящей ноге. Реализация: создание attempt + dispatch.

## 7. Диспетчер и попытки

- [ ] Тест: попытки со статусом `pending` подхватываются диспетчером. Реализация: dispatcher-loop с `FOR UPDATE SKIP LOCKED`.
- [ ] Тест: inline-отправка сразу после создания попытки. Реализация: горячий путь создания → отправка.
- [ ] Тест: восстановление после падения процесса (попытка осталась `pending`). Реализация: повторный проход диспетчера.
- [ ] Тест: синхронная ошибка отправки ведёт на следующую ногу. Реализация: обработка 5xx/таймаута как отказа.

## 8. Вебхуки провайдера и HMAC

- [ ] Тест: вебхук с неверной подписью → 401. Реализация: HMAC-проверка `compare_digest` сырого тела.
- [ ] Тест: `completed` завершает задачу успехом и фиксирует ссылку. Реализация: обработка completed.
- [ ] Тест: `failed` с `technical` ведёт на следующую ногу. Реализация: маршрутизация по типу.
- [ ] Тест: `failed` с `payload` завершает задачу сразу. Реализация: immediate fail.
- [ ] Тест: повторная доставка вебхука дедуплицируется по `(provider,event_id)`. Реализация: `webhook_events` unique + вставка в транзакции.
- [ ] Тест: вебхук в терминальное состояние не меняет статус/деньги. Реализация: terminal guard.

## 9. Сторож (watchdog)

- [ ] Тест: попытка со статусом `sent`, молчащая дольше `PROVIDER_TIMEOUT`, атомарно переводится в `timeout`. Реализация: условный `UPDATE ... RETURNING`.
- [ ] Тест: только один воркер выигрывает переход при конкуренции. Реализация: проверка `rowcount`/RETURNING.
- [ ] Тест: сторож ведёт задачу дальше по правилам отказа. Реализация: общий путь маршрутизации для вебхука и сторожа.
- [ ] Тест: `PROVIDER_TIMEOUT` настраивается (для тестов 60 с). Реализация: чтение из config.

## 10. Правило 6: поздний completed

- [ ] Тест: поздний `completed` после `timeout` не меняет статус и не двигает деньги. Реализация: guard по статусу попытки.
- [ ] Тест: поздний `completed` пишется как `late_completed` в аудит/историю. Реализация: запись события.
- [ ] Тест: задача не получает одновременно результат и возврат. Реализация: инвариант «либо succeeded, либо refund».
