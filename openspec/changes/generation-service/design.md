# Design: Сервис генерации (generation-service)

## Контекст и цели

Сервис принимает заказ на генерацию, списывает токены и передаёт задачу одному из фейковых провайдеров. Критические требования: «ровно один раз» для каждой денежной операции, корректная маршрутизация по цепочке «ног» при отказах, работа в 4+ процессах без задваивания работы сторожа, выживаемость при падении процесса.

## Архитектурное решение: Postgres как source of truth

Надёжность обеспечивается **исключительно** базой данных — без Redis, очередей сообщений и внешних оркестраторов:

- Все переходы состояния и денежные операции — в транзакциях.
- Конкурентные переходы защищены `SELECT ... FOR UPDATE` (блокировка строки задачи/пользователя).
- Идемпотентность денег — уникальные ключи БД (см. ниже).
- Сторож берёт работу через `FOR UPDATE SKIP LOCKED`, чтобы несколько воркеров не обрабатывали одну попытку дважды.

Это осознанный выбор: меньше движущихся частей и проще доказывать корректность, чем с внешней очередью. Trade-off — пропускная способность упирается в Postgres, но для задачи это приемлемо.

## Схема БД

Таблицы (все идентификаторы — UUID, время — `timestamptz` UTC, время берётся из Postgres `now()`, не из Python):

| Таблица | Назначение и ключевые поля |
|---|---|
| `users` | `id`, `balance BIGINT` с `CHECK (balance >= 0)` — материализованная копия, инвариант = `sum(ledger_entries)`. |
| `ledger_entries` | `id`, `user_id`, `kind` (`debit`/`refund`/`topup`), `amount`, `task_id?`, `payment_id?`, `created_at`. Append-only. Уникальность: `(task_id, kind)` для `debit`/`refund` (partial unique), `(payment_id, kind)` для `topup`. |
| `payments` | `id` (= `payment_id`), `user_id`, `tokens`, `status`, `created_at`. Уникальный `payment_id` — идемпотентность оплаты. |
| `models_catalog` | `slug` (PK), `name`, `price_tokens`. |
| `legs` | `id`, `model_slug`, `provider`, `priority`, `max_ref_images`, `skip_on_moderation`. Уникальный `(model_slug, priority)`. |
| `tasks` | `id`, `user_id`, `model_slug`, `price_tokens` (снапшот цены), `status` (`pending`/`running`/`succeeded`/`failed`), `current_leg_id?`, `ref_images_count`, `prompt`, `created_at`, `updated_at`. |
| `attempts` | `id`, `task_id`, `leg_id`, `provider`, `attempt_id` (уникальный), `attempt_no`, `status` (`pending`/`sent`/`succeeded`/`failed`/`timeout`), `error_type?`, `external_id?`, `created_at`, `updated_at`. |
| `webhook_events` | `id`, `provider`, `event_id`, `task_id`, `attempt_id`, `payload_status`, `received_at`. Уникальный `(provider, event_id)` — дедуп вебхуков. |

Порядок блокировок фиксирован: **сначала задача, потом пользователь** (по возрастанию, чтобы не было deadlock). Никаких HTTP-вызовов внутри транзакции — внешний вызов всегда выполняется после коммита переходов.

## Денежные операции и «ровно один раз»

- Списание: строка `ledger_entries(kind='debit')` с уникальностью `(task_id, 'debit')`. Повторная попытка списания по той же задаче упирается в уникальный ключ и откатывается.
- Возврат: `ledger_entries(kind='refund')` с уникальностью `(task_id, 'refund')`. Сколько бы `failed`-вебхуков ни пришло, возврат создаётся один раз.
- Начисление: `ledger_entries(kind='topup')` с уникальностью `(payment_id, 'topup')`; плюс строка в `payments` с уникальным `payment_id`. 20 одновременных одинаковых оплат → одно начисление.
- Всё в одной транзакции: изменение `users.balance` и вставка строки журнала атомарны; `CHECK (balance >= 0)` откатывает уход в минус.
- Инвариант: `users.balance == SUM(ledger_entries.amount)` по пользователю — проверяется в тестах.

## Маршрутизация и попытки

1. `POST /generate` проверяет лимит активных задач (429) и достаточность баланса (402) — именно в этом порядке. Затем, если ни одна нога не подходит — 400 **до** списания.
2. Списание цены (снапшот в `tasks.price_tokens`), создание задачи `running`, создание первой попытки `pending`.
3. Диспетчер (dispatcher loop) выбирает попытку активной задачи со статусом `pending`, блокирует задачу и попытку (`SELECT ... FOR UPDATE`), помечает попытку `sent` (с `sent_at = now()` из Postgres) и коммитит. Затем отправляет HTTP-вызов **вне транзакции**. Упал воркер после создания попытки, но до отправки — попытка останется `pending`, и её подхватит другой воркер (в терминальную попытку она не превращается, поэтому повторного списания нет).
4. Свой `attempt_id` передаётся в `POST /tasks` провайдера; провайдер идемпотентен по `attempt_id` и возвращает его в вебхуке — это даёт корреляцию даже при синхронном таймауте (ответ потерян, но вебхук придёт с тем же `attempt_id`).

## Сторож (watchdog)

- Периодический проход: выборка попыток `status='sent' AND sent_at <= now() - interval PROVIDER_TIMEOUT` (отсечка — из Postgres `now()`).
- Для каждой кандидатки блокируется задача, затем попытка (`FOR UPDATE`), под блокировкой перепроверяется статус `sent` — так переход в `timeout` выигрывает ровно один воркер, остальные видят уже изменённый статус и пропускают.
- Далее идёт по тем же правилам маршрутизации, что и отказ в вебхуке (следующая нога или `failed` + возврат).
- `PROVIDER_TIMEOUT` для тестов — 60 секунд.

## Вебхуки

- Подпись: `X-Signature` = HMAC-SHA256 сырого тела запроса, сравнение через `hmac.compare_digest`. Проверка **до** парсинга тела.
- Дедуп: `webhook_events` с уникальным `(provider, event_id)`; вставка в одной транзакции с обработкой — повторное событие конфликтует по уникальному ключу и игнорируется.
- Обработка: блокировка задачи (`FOR UPDATE`), проверка терминального статуса (guard), затем переход. Терминальное состояние не меняется.

## Правило 6: поздний completed

Если сторож уже перевёл попытку в `timeout` и задача ушла дальше, поздний `completed` игнорируется для денег и статуса: событие пишется в `webhook_events`/историю с пометкой `late_completed`. Это исключает одновременный результат и возврат. Объяснено в README.

## Фейковые провайдеры и управление

- `POST /tasks` → сразу `202 {"external_id": "..."}`; вебхук через 2–20 с (`completed` со ссылкой или `failed` с типом).
- Подпись вебхуков тем же секретом (HMAC-SHA256).
- Настраиваемое поведение: доля отказов и тип ошибки; синхронный отказ (503/таймаут); вебхук дважды (в т.ч. одновременно); вебхук не приходит; `completed` после таймаута.
- Управление: env-дефолты + test-only `PUT /_settings`, включаемый флагом `FAKE_PROVIDER_ADMIN_ENABLED`.

## Осознанные решения

1. **Нет идемпотентности `POST /generate`** — строго по ТЗ. Риск: повторный запрос от клиента создаст вторую задачу и второе списание. Фиксируем в README в «что можно улучшить» (optional `Idempotency-Key`).
2. **429 раньше 402** — лимит активных задач проверяется до баланса.
3. **Без Redis/очередей** — надёжность на Postgres.
4. **Внешний API в `snake_case`** — конфликт с кодстайлом (camelCase) решён в пользу ТЗ.

## Кодстайл и структура (Dima)

- Python 3.13, `uv` + `pyproject.toml`, Black, двойные кавычки, комментарии и docstring на русском, полные тайпинги (`str | None`).
- Структура: `src/` с `handlers/routers/schemas/services(queries+uow)/database/models.py/utils/telemetry/config.py/main.py`.
- `NullPool` для async SQLAlchemy; multi-stage Docker; gunicorn + UvicornWorker (4 воркера).
- OpenTelemetry-модуль с `OTEL_ENABLED=false` по умолчанию.

## Тестирование

- Обязательные интеграционные: реальный HTTP к live compose (4 воркера) + проверка БД: 20 одновременных оплат → 1 начисление; 10 одновременных `failed` на последней ноге → 1 возврат; отказ первой ноги → завершение на второй (2 попытки в истории); поздний `completed` после сторожа → правило 6.
- Юнит-тесты через `ASGITransport` (без реального сервера).

## Что можно улучшить

- `Idempotency-Key` для `POST /generate`.
- Внешняя очередь вместо dispatcher-loop для большей пропускной способности.
- Настоящее объектное хранилище для результатов.
