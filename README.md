# Generation Service

Сервис генерации: принимает заказ, списывает токены, отдаёт задачу одному из
фейковых провайдеров (`alpha` / `beta`) по цепочке «ног». Если провайдер отказал —
идёт к следующему, если отказали все — возвращает токены. Каждое движение денег
происходит **ровно один раз**.

## Стек

Python 3.13, FastAPI, SQLAlchemy 2 (async) + asyncpg, PostgreSQL, Alembic,
pytest + pytest-asyncio. Управление зависимостями — `uv`.

## Запуск

```bash
docker compose up -d --build
```

Поднимает:

- `db` — PostgreSQL;
- `migrate` — применяет миграции Alembic (one-shot);
- `app` — сервис в **4 воркерах** (gunicorn + UvicornWorker), порт `8000`;
- `alpha` — фейковый провайдер, порт `8001`;
- `beta` — фейковый провайдер, порт `8002`.

Если порты заняты — переопределите их:

```bash
APP_PORT=8100 ALPHA_PORT=8101 BETA_PORT=8102 docker compose up -d --build
```

### API

| Запрос | Описание |
|---|---|
| `POST /generate` | `{user_id, model_slug, prompt, ref_images}` → `{task_id}`. `402` нет токенов, `429` 3 активные задачи, `400` нет подходящей ноги |
| `POST /webhooks/providers/{name}` | результат от провайдера (`completed`/`failed`), подписан HMAC |
| `POST /webhooks/payments` | `{payment_id, user_id, tokens, status}`, подписан HMAC |
| `GET /tasks/{id}` | статус, текущая нога, история попыток |
| `GET /users/{id}/balance` | баланс и последние строки журнала |

Подпись: `X-Signature = HMAC-SHA256(сырое тело, WEBHOOK_SECRET)`. Общий секрет
одинаковый для провайдеров и платежей.

## Тесты

Юнит-тесты (ASGI, настоящий PostgreSQL из compose):

```bash
docker compose up -d db
uv run pytest -m "not integration"
```

Интеграционные тесты (живой compose-стек с 4 воркерами, обязательные сценарии):

```bash
# стек с быстрыми таймаутами и включённым admin-эндпоинтом провайдеров
docker compose -f docker-compose.yml -f docker-compose.test.yml up -d --build
TEST_BASE_URL=http://localhost:8000 uv run pytest tests/integration
```

Обязательные сценарии покрыты в `tests/integration/test_exactly_once.py`:

- 20 одновременных одинаковых вебхуков оплаты → одно начисление;
- 10 одновременных `failed` на последней ноге → один возврат;
- отказ первой ноги → завершение на второй (в истории две попытки);
- поздний `completed` после сторожа → правило 6.

## Миграции

Схема создаётся Alembic (`alembic/`). Применяются автоматически сервисом
`migrate` при `docker compose up`, либо вручную:

```bash
uv run alembic upgrade head
```

Добавление следующей миграции:

```bash
# после изменения models.py
uv run alembic revision --autogenerate -m "описание изменения"
uv run alembic upgrade head
```

Стартовый каталог (`image-fast`, `video-long` и их ноги) наполняется
data-миграцией `0001_initial`.

## «Ровно один раз»

Каждое движение денег защищено на уровне базы, а не кода:

- **Списание** — строка `ledger_entries(kind='debit')` с уникальным частичным
  индексом `(task_id, kind) WHERE kind IN ('debit','refund')` + уменьшение баланса
  в той же транзакции создания задачи.
- **Возврат** — строка `kind='refund'` с тем же уникальным индексом. Сколько бы
  `failed`-вебхуков ни пришло, возврат создаётся один раз: вставка через
  `INSERT ... ON CONFLICT DO NOTHING`, баланс увеличивается только если строка
  реально вставлена.
- **Начисление** — `payments.payment_id` уникален + `kind='topup'` с уникальным
  `(payment_id, kind) WHERE kind='topup'`. 20 одновременных одинаковых оплат
  конфликтуют по уникальному ключу, начисляет только одна.

Дополнительно:

- **Блокировки строк**: `SELECT ... FOR UPDATE` на пользователе (генерация) и на
  задаче (вебхуки, сторож). Фиксированный порядок блокировок — задача → пользователь,
  чтобы не было deadlock. Никаких HTTP-вызовов внутри транзакции.
- **Инвариант баланса**: `users.balance == SUM(ledger_entries.amount)`; изменение
  баланса и строка журнала пишутся атомарно, `CHECK (balance >= 0)`.
- **Дедуп вебхуков провайдера**: `webhook_events` с уникальным `(provider, event_id)`;
  вставка в одной транзакции с обработкой.

## Падение процесса посреди обработки вебхука

Вебхук обрабатывается в одной транзакции: дедуп-вставка + переход состояния +
(при необходимости) возврат. Если процесс падает до commit — транзакция
откатывается целиком, и провайдер доставляет вебхук повторно (at-least-once).
Повтор идемпотентен:

- повторная доставка ловится уникальным `(provider, event_id)` и возвращает `200`;
- даже если событие новое (другой `event_id`), терминальный guard по статусу задачи
  и уникальный ключ возврата не дают двигать деньги повторно.

Попытка отправки задачи провайдеру тоже переживает падение: сначала попытка
создаётся в БД со статусом `pending`, а диспетчер (фоновый цикл в каждом воркере)
забирает её через блокировку. Упал воркер после создания попытки — другой
подхватит. Сторож и диспетчер запущены в каждом из 4 воркеров, но корректность
обеспечена блокировками БД, а не состоянием процесса.

## Правило 6: поздний `completed` после сторожа

Если провайдер молчит дольше `PROVIDER_TIMEOUT`, сторож снимает попытку
(`status='timeout'`) и ведёт задачу дальше (следующая нога или возврат). Когда
после этого приходит поздний `completed`, сервис **игнорирует** его для денег и
статуса: попытка помечается `late_completed`, событие пишется в аудит
(`webhook_events`), ответ `200`. Так задача не получает одновременно и результат,
и возврат — гарантируется тем, что возврат выполняется только при переходе в
`failed`, а результат — только при переходе в `succeeded`, и оба перехода защищены
блокировкой задачи.

## Что можно улучшить

- `Idempotency-Key` для `POST /generate` — сейчас повторный запрос клиента
  (например, retry после таймаута ответа) создаст вторую задачу и второе списание.
  Осознанно не добавлено (строго по ТЗ), но для прода это первое, что стоит сделать.
- Внешняя очередь (вместо dispatcher-loop) для большей пропускной способности.
- Настоящее объектное хранилище для файлов результата (сейчас — строка-ссылка).
- Пул соединений (вместо `NullPool`) или PgBouncer при росте нагрузки.
